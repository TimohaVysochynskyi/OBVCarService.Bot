# План рефакторингу

Робочий документ. Кожен крок — окрема сесія, окремий коміт, окремий відкат.
Після завершення всього — видалити цей файл, а те, що лишилось актуальним, перенести в `CLAUDE.md`.

## Навіщо

Доменна дисципліна в проєкті сильна: докази перевіряються кодом, а не довірою до моделі; кожна таксономія живе в одному файлі; пастки зафіксовані. **Структурної** дисципліни немає:

| проблема | вимір | наслідок |
|---|---|---|
| `store.js` тримає весь SQL обох процесів | 68 КБ, ~90 функцій | зміна SQL звіту може зламати інжест |
| тести живуть поза репозиторієм | 412 асерцій у скретчпаді | зникнуть разом із сесією; рефакторинг наосліп |
| `process.env` читається при імпорті в десятках модулів | ~25 місць | порядок імпортів впливає на поведінку |
| міграції — імперативний код у `migrate()` | ~250 рядків | немає історії, неможливо відкотити, помилка кладе бота на старті |
| HTTP до OpenAI робить кожен модуль сам | 12 місць | ліміт 30k токенів/хв обходиться паузами вручну; вартість — оцінка, не факт |
| `globalReportHtml.js` — конкатенація рядків | 37 КБ | одна функція на весь документ |
| прогрес перерахунку в пам'яті бота | `reprocess.js` | `pm2 reload` губить роботу |

## Принципи

1. **Рефакторинг не змінює поведінку.** Жодної «заодно покращеної» логіки в тому ж комміті. Інакше регресію неможливо знайти.
2. **Тести йдуть попереду.** Крок 1 — умова для кроків 3 і 5; без нього вони надто ризиковані.
3. **`domain/` не імпортує `platform/`.** Правило перевіряється тестом, а не домовленістю.
4. **Кожен крок окремо деплоїться.** Якщо після кроку 3 захочеться зупинитись — проєкт лишається в робочому стані.
5. **Інваріанти не ослаблюються.** Перевірка цитат проти сегментів менеджера, `MIN_EVIDENCE`, `unchecked` замість `none`, `temperature: 0` у детекторі відмов — усе переживає переїзд без змін.

## Чого НЕ робимо

| що | чому |
|---|---|
| TypeScript одразу | виграш менший, ніж від кроків 1-3. Вводити пофайлово **після** того, як межі проведені — через JSDoc + `checkJs`, без кроку збірки |
| DI-контейнер, Nest, фреймворк | два процеси — оверкіл, який коштує більше, ніж вирішує |
| ORM замість сирого SQL | запити тут складні й вивірені (`SALES_FILTER`, `reachableCount`, MODE слабкого етапу); ORM їх лише заплутає |
| зміна доменних правил «заодно» | рефакторинг, який одночасно покращує логіку, — це рефакторинг, у якому неможливо знайти регресію |
| React / збірка фронтенду звіту | документ має відкриватись із файлу без інтернету; інлайн-SVG і статичний `app.js` цю вимогу виконують |

## Порядок і віддача

```
1. тести           ← умова безпеки для решти
2. конфіг+міграції
3. розбити store   ← ~80% користі досягнуто тут
4. LlmClient
5. переїзд дерева
6. компоненти звіту
7. черга джобів
```

Зупинитись можна після будь-якого кроку — проєкт лишається робочим.

## Чи можна робити кроки автономно

| крок | автономно | що потрібно від власника |
|---|---|---|
| 1. тести | **так, повністю** | нічого |
| 2а. конфіг | **так** | нічого |
| 2б. міграції | так, але | прогін на VPS проти реальної БД (з dev-машини вона недоступна) |
| 3. розбити store | **так** | нічого до деплою; після — звичайний `git pull && pm2 reload` |
| 4. LlmClient | **так** | нічого (тести на fake-клієнті, без витрат) |
| 5. переїзд | **так** | на VPS `pm2 delete && pm2 start` замість `reload` |
| 6. компоненти звіту | **так, повністю** | нічого (рендер із дампа коштує 0) |
| 7. черга джобів | так, але | перевірка «переживає рестарт» — лише на VPS |

**Спільні обмеження:**
- БД локальна на VPS → усе, що торкається SQL, остаточно перевіряється там, а не на dev-машині.
- Довгі прогони на VPS — тільки `nohup … > лог 2>&1 & disown`.
- Деплой і рестарт процесів — з відома власника, не мовчки.

**Кожна сесія починається й закінчується у відомому стані:** `npm test` зелений, зміни закомічені, `CLAUDE.md` оновлений. Тому наступна сесія може починати з чистого контексту, прочитавши лише `CLAUDE.md` і цей файл.
