This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Обов'язок підтримувати цей файл

**Кожного разу, коли вносиш зміну в архітектуру, флоу, env-змінні, схему БД, job-типи чи розклад — онови відповідний розділ цього файлу в тому ж дифі.** Це не окрема задача "колись потім", а частина самої зміни. Якщо додав нову таблицю/колонку — онови "Схема БД". Якщо змінив логіку — онови "Архітектура" і "Env-змінні". Якщо переніс щось зі статусу "заплановано" в "зроблено" — онови "Поточний статус". Мета — щоб наступний інстанс Claude Code міг зрозуміти реальний стан проєкту з цього файлу, не перечитуючи всю історію чату.

## Робочий процес: уточнюючі питання

**Щоразу після прочитання промпту користувача та його аналізу — перш ніж писати код — став уточнюючі питання, якщо в задачі є неоднозначності** (інструмент `AskUserQuestion`). ## Що це за проєкт

Автоматизація для клієнта (СТО/автосервіс): дзвінки менеджерів через Binotel (АТС) автоматично транскрибуються через OpenAI, класифікуються (успішність / найслабший етап / оцінка) і **зберігаються в Postgres із прив'язкою до конкретного менеджера**; окремий Telegram-бот читає ту саму БД і віддає звіти/статистику/архів. Раніше було на n8n; переписано на чистий Node.js, деплой — VPS (AlmaLinux) під pm2: два процеси (cron-інжест + persistent-бот) з одного репо.

**Два компоненти (монорепо):**
1. **Інжест** (`src/jobs/`, pm2 cron-джоб `obv-poller`, `*/15`) — збір, транскрипція, класифікація і атрибуція дзвінків у БД. Звітів тут немає свідомо.
2. **Бот звітності** (`src/bot/`, pm2 persistent-процес `obv-bot`) — інтерактивний Telegram-бот (grammy, long-polling): авто-звіти, статистика менеджера, архів розмов, база знань (RAG). Читає ту саму БД. **Той самий єдиний бот** `@OBVCarServiceWork_bot`, що й алерти інжесту.

Раніше в інжесті були PDF-звіти в Telegram + Google Sheets — видалено. Google Sheets вирізано повністю. **PDF також прибрано:** звіт менеджера тепер **доказовий** (evidence-first) — короткий текст findings + **аудіо-фрагменти** з реальних дзвінків, доставляється в Telegram (не PDF). Деталі — розділ «Доказовий звіт» нижче.

Пріоритети клієнта, які визначили архітектурні рішення: мінімізація регулярних витрат (усе на безкоштовних/копійчаних тарифах, де можливо) і надійність (жодні дані не повинні губитись мовчки).

Запускати ПІСЛЯ будь-якої зміни чанкінгу або того, що йде в embedding

У кінці очищає кеш `report_segments` (щоб findings перерахувались із блокерами) — `-- --keep-cache` вимикає це, `-- --limit N` для смоук-тесту

Non-zero exit на неповний прогін (як `kb:reindex`), тож можна ганяти в циклі
npm run backfill:clientnumbers             # одноразово: заповнити НОМЕР і ІМ`Я клієнта (client_number/client_name) для дзвінків, збережених до появи цих полів — лише перезапит Binotel list-of-calls-for-period + запис у БД (без re-STT/LLM); ідемпотентно (кожна колонка під власним `IS NULL`, наявні значення не перезаписуються)

Тестів і лінтера в проєкті немає. Перевірка коректності — `node --check src/*.js` (синтаксис) + реальний прогін проти живих Binotel/OpenAI/Postgres креденшлів з `.env` (⚠️ БД тепер локальна на VPS — з dev-машини вона зазвичай недоступна, тож інтеграційні прогони роби на VPS; чисту логіку без БД/мережі можна юніт-тестити локально, напр. `assembleFindings`/`findQuote`) (усе покрито живими тестами по ходу розробки, автоматизованого test suite нема).

Код на **ESM** (`import`/`export`, `"type": "module"` в package.json). Відносні імпорти — з розширенням `.js`. CJS-залежності підключаються через default-import (напр. `import pg from 'pg'; const { Pool } = pg;`).

## Структура репо

Монорепо, feature-based. Стандарт узгоджено під майбутній окремий бот звітності:

```
src/
  core/     — спільне ядро (використовують і jobs/, і bot/):
              store, binotel, audioStore (локальний архів записів), transcribe, elevenlabs, classifyCall,
              analyzeCall (per-call MAP), dealBlocker (незакриті угоди), dialogueMetrics (перебивання/паузи),
              quoteMatch (fuzzy цитата→таймкод), identifyManager, telegram, retry
  jobs/     — задеплоєний cron-джоб (інжест): index.js (entrypoint) + pollNewCalls + processCalls
  scripts/  — одноразові інструменти: backfill, testSingleCall, reattributeShared, retranscribeRecent, backfillAnalysis, reindexKb
  bot/      — Telegram-бот звітності (grammy, окремий токен, окремий сервіс):
              index.js (entrypoint) + keyboards + stats + dynamics (екран росту) + archive + report + segments (кеш аналітики по відрізках) +
              analyze (REDUCE + self-consistency) + audioClip (ffmpeg-нарізка) + prompt (хаб редагованих інструкцій AI) + kb + kbClip (нарізка PDF-сторінок) + time + ui
              (див. src/bot/README.md)
```

Коли пишеться нижче просто "processCalls.js", "store.js" тощо — шукати за цією мапою (`core/`, `jobs/` чи `bot/`).

## Архітектура

**Один cron-джоб** (pm2 `obv-poller`, `cron_restart: */15 * * * *`, `JOB_TYPE=poll`) робить усе:

1. **`retryPendingCalls()`** (`processCalls.js`) — спершу ретраїть усе, що застрягло в `pending_calls` з минулих разів
2. **Поллінг** (`pollNewCalls.js`): чекпоінт (`app_state.last_polled_until`) → зараз. Не фіксоване "останні N хв" — щоб пропущений/затриманий cron-запуск не створював діру. `listCallsForPeriod` (Binotel) обмежений 24 год на запит, тому діапазон ріжеться на шматки по 23 год (`processCalls.js: splitIntoChunks`)
3'. Після класифікації, **якщо угода НЕ закрилась** — `detectDealBlocker` (`core/dealBlocker.js`, `gpt-4o`): чи не взяло клієнта саме СТО (черга / не наш профіль). Див. «Незакриті угоди» нижче.
3. Для кожного нового дзвінка: якщо `durationSec <= 0` — пропустити (не відповіли); якщо `recordingStatus != 'uploaded'` — в `pending_calls` на ретрай; інакше — **`storeRecording` (завантажити запис з Binotel ОДИН раз і зберегти на диск, див. «Локальний архів записів» нижче)** → `transcribeAudio(buffer)` (див. «Транскрипція» нижче, повертає `{transcript, segments}`) → **резолвинг імені оператора** (див. нижче) → **per-call MAP** `analyzeCallBehaviors` (`core/analyzeCall.js`, `gpt-4o-mini`: визначає **мету дзвінка** `callPurpose` й, лише для продажних, тегує поведінки менеджера + дослівні цитати, КОД привʼязує таймкоди через `quoteMatch.findQuote`) → **ГЕЙТ ЗА МЕТОЮ:** `classifyCall` (легкий запит: успішність / найслабший етап / оцінка 1-10) виконується **ЛИШЕ якщо `callPurpose === 'sales'`**; для непродажних (`info`/`other`) `classifyCall` **не викликається взагалі** (нуль ресурсу на оцінку ефективності), а `is_success`/`weakest_stage`/`communication_score` = NULL → `saveCall` в Postgres (транскрипт + `segments` + `behaviors` + `call_purpose` + класифікація-або-NULL + `manager_name` разом). **Порядок навмисний** (Задача 1): мета визначається ПЕРШОЮ, і ефективність оцінюється тільки на продажних дзвінках. MAP не фатальний: якщо впав — мета невідома → трактуємо як `sales` (робимо `classifyCall`, щоб не втратити оцінку на збої) і зберігаємо без `behaviors` (беклог полагодить пізніше).

## Незакриті угоди: коли винне СТО, а не менеджер (`core/dealBlocker.js`, 2026-07-30)

Угода, що не закрилась, бо **саме СТО не могло взяти роботу**, раніше рахувалась провалом менеджера і тягла його конверсію вниз за те, чого він не міг продати.

- **РІВНО ДВІ категорії** (рішення власника) — вони ж дві колонки в «Динаміці». Розділяє їх ОДНЕ питання: «чи взяли б цього клієнта ІНШОГО ДНЯ?»
  - **`no_slot` → колонка «Черга»** — ТИМЧАСОВО немає часу/місця/людини: «усе забито», «черга на два тижні», «майстер у відпустці», «підйомники зайняті».
  - **`out_of_scope` → колонка «Профіль»** — НЕ надаємо цього взагалі: не той тип авто, немає такої послуги, немає обладнання, потрібну запчастину не дістати.
- **Точність важливіша за повноту, бо базова частота МІКРОСКОПІЧНА.** Заміряно на живих даних: за 6 тижнів (811 дзвінків) справжніх блокерів **0-3**. При такій частоті детектор із 5% хибних спрацювань «знайшов» би десятки блокерів, потопив би справжні і — оскільки заблоковані дзвінки виходять зі знаменника конверсії — **тихо покращив би показники всіх менеджерів**. Тому три запобіжники:
  1. модель **зобов'язана** повернути ДОСЛІВНУ репліку менеджера;
  2. **КОД** заново знаходить цю цитату в сегментах менеджера (`findQuote requireRole:'manager'`) — не знайшов, значить блокера немає;
  3. **окремий суворий прохід-рецензент**, який **за замовчуванням ВІДКИДАЄ** (той самий патерн, що `verifyFindingsRelevance` для findings). Помилка рецензента = відмова, а не блокер.
  Заміряно на розміченому наборі: **11/11 правильно, 0 хибних на 20 контрольних дзвінках**. Один прохід без рецензента давав **~1 хибне з 3**.
- ⚠️ **Пастки мови автосервісу, знайдені в РЕАЛЬНИХ транскриптах цього акаунта** (усі вписані в промпт — не прибирати):
  - **«забитий» у СТО зазвичай означає ЗАСМІЧЕНИЙ вузол**, а не завантажений графік: «радіатори забиті», «фільтр був забитий», «сітка забита». Це діагностика деталі, а не відмова.
  - **«робимо, не робимо»** — менеджер пропонує КЛІЄНТУ вирішити, а не відмовляє.
  - **Клієнта записали на ІНШУ дату — це ЗАКРИТА угода, не блокер.** Реальний кейс 6685362217: клієнт питає «у вас усе забито на сьогодні?», менеджер: «Да, забито сьогодні дурдом» — і тут же записує його на п'ятницю. Рецензент правильно відкинув це; моя початкова розмітка була ХИБНОЮ, а не детектор.
  - Роздуми менеджера («треба, щоб хтось знаючий подивився») — не відмова.
- **Модель — `OPENAI_BLOCKER_MODEL`, дефолт `gpt-4o`** (не `mini`, як решта per-call аналізу) на пряме прохання власника. ⚠️ Ліміт акаунта — **30k токенів/хв**, а звіти (`OPENAI_REPORT_MODEL`) ділять цю саму квоту, тож ретраї тут довші (4 спроби × 4с), а беклог **обов'язково** з паузою 2.6с.
- **Коли перевіряється:** лише якщо угода НЕ закрилась (`isSuccess !== true`) — закрита угода не може бути заблокована, і це тримає вартість gpt-4o мізерною. **НЕ гейтиться за `call_purpose`:** заміряно, що такі дзвінки MAP зазвичай класифікує як `info` (він бачить відмову, а не можливість продажу), тож гейт по `sales` не зловив би майже нічого.
- **Вплив на числа:** конверсія тепер по **доступних** угодах (`reachableCount` = закриті + незаблоковані), і `weakest_stage` MODE ігнорує заблоковані — інакше «закриття угоди» очолювало б «Проблемні сегменти воронки» просто тому, що СТО було забите. ⚠️ У `reachableCount` навмисно є `OR is_success`: `backfill:analysis`/`rescore:sales` перезаписують `is_success` пізніше, і якби вони колись зробили заблокований дзвінок успішним, знаменник без цього дав би конверсію >100%.
- **У звіті** — окремий блок, що показується навіть за **ОДИН** випадок (свідомо НЕ прив'язаний до `MIN_EVIDENCE`, бо це порахований факт із БД, а не LLM-патерн): категорія, час, **ім'я і телефон клієнта** (щоб директор міг перетелефонувати, коли звільниться місце) і дослівна цитата менеджера. Плюс компактний блок у заголовку.
- **У «Динаміці»** заглушки `Перша`/`Друга` замінені на `Черга`/`Профіль`. Бакет, який ще не перевіряли, показує **`—`, а не `0`** — «не перевіряли» і «нікому не відмовили» не повинні виглядати однаково.

**Локальний архів записів (`core/audioStore.js`, 2026-07-30).** До цього аудіо **ніде не зберігалось**: інжест брав у Binotel URL запису, віддавав його транскрайберу і забував — тобто запис існував лише поки його тримає Binotel, а кожне прослуховування/нарізка коштували два запити до Binotel. Клієнт вимагає зберігати ВСІ записи, тому тепер інжест **завантажує файл один раз, кладе на диск VPS і транскрибує з тих самих байтів**.

- **Розкладка:** `<AUDIO_STORAGE_DIR>/YYYY-MM/<generalCallId>.mp3` (дефолт `<repo>/data/recordings`, у `.gitignore`). Місяць беруть зі `start_time` дзвінка; папки-місяці тримають кожен каталог малим (~600 файлів/міс) і дають людині/бекапу зрозумілу структуру. Відносний шлях пишеться в `calls.audio_path`, щоб ніхто його не вгадував.
- **Розміри (заміряно на живому акаунті 2026-07-30):** Binotel віддає **mp3 32 kbps моно, ~4 КБ/с**, тобто ~268 КБ на середній 67-секундний дзвінок. Уся наявна історія (806 дзвінків, 15.0 год) — **~216 МБ**; при ~19 дзвінках/день це **~150 МБ/міс, ~1.8 ГБ/рік**. На диску VPS вільно 16 ГБ. Перекодування безглузде на 32 kbps, тому файл зберігається **байт-у-байт як є**.
- **Хто читає локально (замість Binotel):** аудіо-кліпи доказового звіту (`bot/audioClip.js` — ffmpeg ріже прямо збережений файл, **без жодного завантаження**), «🎧 Прослухати запис» в архіві, і всі скрипти перетранскрибації/переаналізу (`backfill:analysis`, `retranscribe:recent`, `retranscribe:last`). Спільна точка входу — `getRecordingForCall(gid)`: локальний файл → інакше Binotel (і одразу архівує завантажене). **Наслідок:** повторний аналіз історії більше не залежить від того, чи Binotel досі тримає запис.
- ⚠️ **Шлях залежить від `start_time`**, тому той, у кого є лише `general_call_id`, ЗОБОВ'ЯЗАНИЙ узяти рядок з БД (`getCallAudio`), а не вгадувати папку — інакше шукав би в чужому місяці й даремно перезавантажував. Саме тому `getRecordingForCall` існує як єдина точка входу.
- **Запис атомарний** (`.part` + `rename`): недописаний через збій/повний диск файл інакше назавжди виглядав би як валідний запис, і всі наступні читачі отримували б обрізане аудіо.
- **Збереження — best-effort і НІКОЛИ не фатальне:** якщо диск повний/read-only, `storeRecording` усе одно повертає байти, дзвінок транскрибується й зберігається, а в БД лягає `audio_status='unavailable'`. Проблема з диском деградує до «цей дзвінок не заархівовано», а не «дзвінок втрачено».
- **Дзвінки з `EXCLUDED_EXTENSIONS` (мобільний директора) архівуються ЯК АУДІО** (рішення власника 2026-07-30), але **більше нічого**: без транскрипції, аналізу й рядка в `calls` — тобто статистика менеджерів лишається чистою, як і була. Файл на диску і є записом (`audio_path` для них ніде не зберігається). Якщо запис ще не `uploaded` — такий дзвінок кладеться в `pending_calls`, і `retryPendingCalls` архівує аудіо та прибирає рядок (інакше аудіо губилось би тільки через те, що чекпоінт уже проїхав це вікно).
- **Watchdog диска** (`jobs/pollNewCalls.js: checkAudioDiskSpace`): архів вічний, тож місце тільки закінчується. Один алерт при перетині `AUDIO_MIN_FREE_MB` (деф. 1024) вниз, переозброюється, коли місце звільнили — той самий патерн дедупу, що й у балансу ElevenLabs (`app_state.audio_space_state`).
- **Бекап поза VPS — свідомо НЕ робимо** (рішення власника 2026-07-30: «поки лише VPS»). Тобто якщо диск/VPS помре, аудіо помре разом із ним, як і БД. Це усвідомлений компроміс, а не недогляд — окрема задача на майбутнє.

**Транскрипція (`core/transcribe.js` + `core/elevenlabs.js`).** `transcribeAudio(audio, {managerName, audioPath})` приймає **байти** (Buffer/Blob — нормальний шлях: інжест уже має завантажений файл) або URL-рядок (легасі-шлях для `test:call`). `audioPath` дає ffprobe читати збережений файл напряму, без повторного запису в temp. **Первинний шлях — ElevenLabs STT (Scribe):** `POST /v1/speech-to-text` робить транскрипцію + **розділення мовців в одному виклику**. **Стерео vs моно:** `core/audioMeta.js: probeChannels` (ffprobe) визначає к-сть каналів; для **стерео** вмикаємо мультиканальний режим (`use_multi_channel:true`, `diarize:false`, `multichannel_output_style:combined`) — кожен канал = окрема сторона, тож поділ мовців **ідеальний** (беремо прямо з ElevenLabs, без контент-здогадок; слова несуть `speaker_id`/`channel_index`). Для **моно** — контент-діаризація (`diarize:true`), як раніше. Роль «хто менеджер» усе одно вирішує `pickManagerSpeaker`, але на чисто розділеному стерео-тексті це набагато надійніше. Нема ffprobe → тихо працює як моно. З `words[]` (кожне слово має `speaker_id`) збираємо репліки (`buildTurns`) і зберігаємо **готовий діалог «Менеджер:/Клієнт:»** прямо як `transcript`. **Хто саме менеджер (`pickManagerSpeaker(turns, speakerIds, managerName)`)** — шукаємо НАШОГО працівника (не «того, хто грає роль оператора»: на вихідному дзвінку наш менеджер сам телефонує й звучить як замовник — рольова логіка там плутається). Відоме імʼя менеджера прокидається сюди (`processCalls` → `call.employeeName`; скрипт перетранскрибації → `op.name`). Шари, найнадійніший перший: (1) **самопредставлення** `selfIntroManager` — детерміновано: якщо мовець каже «це/это `<Ім'я>`», «`<Ім'я>` вас турбує/беспокоит», «мене звати `<Ім'я>`» → це наш менеджер (ловить кейс, коли менеджер сам телефонує); (2) **LLM** по всьому діалогу, з іменем переформатований на «хто з мовців — наш працівник «`<Ім'я>`»» (або, без імені, на «хто оператор СТО»), + reasoning/confidence; (3) **keyword-евристика** `heuristicManager` (оператор-маркери uk/ru) і перший мовець — як резерв. ⚠️ Content-методи мають стелю (дзвінки без імені + неоднозначні ролі); остаточно надійний шлях — **голосовий відбиток** (планова задача, див. статус). Тобто розділення мовців відбувається на інжесті, а не при відкритті архіву → архів миттєвий. **`transcribeDiarized` повертає `{ transcript, segments }`:** окрім готового рядка, зберігаємо `segments` — репліки з **таймкодами** `start/end` кожного слова (`buildTurns` тепер їх НЕ викидає) у форматі `[{role:'manager'|'client', text, start, end}]` (колонка `calls.segments` JSONB). Таймкоди потрібні доказовому звіту, щоб вирізати аудіо-фрагмент навколо цитати. На OpenAI-fallback (без діаризації) `segments = null` → цитати без аудіо. **Fallback — OpenAI** (якщо нема `ELEVENLABS_API_KEY` / API впав / вичерпано кредити): стара логіка — транскрипція з укр-ухилом → детекція spoken-vs-written (суржик = uk) → перетранскрибація з примусовою мовою, якщо не збігається (фікс «українську записало як російську»). `CALL_LANGUAGE` (env) форсить мову для обох шляхів. Тариф ElevenLabs для ~50 дзв/день — **Scale** (STT = 330 кредитів/хв; ~1,5 млн кредитів/міс).

Ніякої звітності на кожному запуску вже немає — це кінець флоу інжесту.

### Бот звітності (`src/bot/`, окремий persistent-процес під pm2, long-polling grammy)

Персистентний процес (не cron), стартує `bot.start()`.

**Система ролей / контроль доступу (`bot/access.js` + `bot/roles.js`, таблиця `bot_users`).** Доступ більше НЕ керується env-allowlist'ом — ролі живуть у БД. Ролі — фіксований ENUM (без «додати роль»):
- **director** та **marketer** — однаковий ПОВНИЙ доступ (admin-tier): **доказовий звіт** по всіх, архів, база знань (питання+файли), промпт аналізу, керування ролями.
- **manager** — «📊 Моя статистика» (ЛИШЕ числовий блок по собі + свій телефон, **БЕЗ** доказового звіту й AI-аналізу) і база знань (питання). Ідентичність — через `bot_users.operator_name` (директор лінкує при додаванні), тож у статистику по собі природно входять і дзвінки зі спільних номерів, атрибутовані на те саме ім'я. **Доказовий звіт з аудіо — інструмент керівника, менеджеру недоступний.**
- **mechanic** — лише база знань (питання).

`access.js`: `getUser` (роль по `telegram_id`, кеш із `invalidateRole`), `canAccess(role, feature)` + `featureOf(ctx)` — центральний gate в auth-middleware (класифікує кожен апдейт у фічу й пускає/блокує). `mainMenu(role)` і нативні команди (`setMyCommands` зі `scope:{type:'chat'}`) підбираються під роль. **Bootstrap:** `seedDirectors()` на старті сідить user-id з `TELEGRAM_BOOTSTRAP_CHAT_IDS` як директорів (щоб не залочитись), відсіюючи негативні (групові) id — ролі прив'язані до `ctx.from.id` (user).

**Керування ролями (`roles.js`, admin-only, блок «👥 Ролі» / `/roles`):** кнопки Маркетологи/Менеджери/Механіки (директорів UI навмисно не чіпає — захист seed-власника від видалення). Роль → список людей + «➕ Додати» → людина → «🗑 Видалити». **Додавання** (Telegram не дає ботам шукати за `@username` — це навмисне обмеження приватності): (1) `request_users` — обрати колегу з контактів, отримуємо `user_id`(+ім'я/username) МИТТЄВО, без потреби, щоб людина спершу писала боту (Bot API 7.2, grammy `Keyboard.requestUsers`); (2) поділитися контактом (є `user_id` → active, інакше pending за телефоном); (3) ввести телефон → pending. **Pending → active:** незнайомець ділиться СВОЇМ контактом на `/start`, `activatePendingByPhone` матчить за останніми 9 цифрами. Для manager після додавання — вибір оператора з roster (`getOperators`) → `operator_name`. ⚠️ Навіть маючи `user_id`, бот не може написати людині першим, поки вона не натисне Start (правило Telegram) — тож особисті авто-звіти неможливі; «Мій звіт» менеджер тягне сам інтерактивно.

**Навігація:** (1) нативні команди — кнопка «Menu» біля поля вводу, **список підбирається під роль** (`setMyCommands` зі `scope:{type:'chat'}`): admin — `/menu /stats /archive /ask /files /report /prompt /roles /settings`; manager — `/menu /myreport /ask`; mechanic — `/menu /ask`; (2) inline-меню в повідомленнях (`keyboards.js: mainMenu(role)`) + inline «« Назад до меню» на всіх екранах. Постійну reply-клавіатуру (`quickKeyboard`/`QUICK`) **прибрано** (забагато UI-навантаження) — `/start` шле `remove_keyboard`, щоб очистити її в старих клієнтів. Нативний список команд свідомо ширший за inline-меню: **`/files` (Файли) і `/settings` (Налаштування) є ЛИШЕ в нативному списку**, inline-кнопок для них немає (свідомо, щоб не перевантажувати меню). Inline-кнопки admin-меню: «📊 Статистика менеджера», «🗂 Архів розмов», «📚 База знань» (`kb:ask`), «🔄 Звіт зараз», «👥 Ролі».

**Модель «активного екрана»** (`bot/ui.js: showScreen()`, замінила прямі `editMessageText`): меню/пікер завжди живе в НАЙнижчому повідомленні, щоб фокус юзера (низ чату) збігався з дією. Якщо натиснуте меню ще внизу — редагуємо на місці (плавно, без спаму); якщо його «поховало» під контентом (транскрипт / відповідь KB / текст промпту) — надсилаємо свіже меню внизу й видаляємо старе. `installMessageTracker` (API-transformer) веде id останнього надісланого ботом повідомлення на чат (щоб знати, чи меню ще внизу); `ctx.session.screenId` — id активного екрана (для видалення старого). Контентні дії (перегляд промпту тощо) після себе ре-планують меню вниз. Best practice підтверджено пошуком (стандарт — edit-in-place; тут адаптовано під контент-важкий бот).

**Доказовий звіт (evidence-first, map→reduce з кешем).** Замість узагальненої прози — findings, кожен підкріплений **≥`MIN_EVIDENCE` (=2, було 3) реальними, релевантними цитатами**, до негативних — **аудіо-фрагменти**. Шари:
- **MAP** (`core/analyzeCall.js`, per-call, `gpt-4o-mini`, на інжесті) — спершу визначає **тип дзвінка** (`callPurpose`: `sales`/`info`/`other`) і зберігає його в `calls.call_purpose`. **Поведінки тегуються ЛИШЕ для `sales`-дзвінків** (інформаційний «машина готова» / підтвердження запису / клієнт уточнює статус → 0 поведінок, щоб непродажна розмова не стала «помилкою продажу»). Цитати приймаються ЛИШЕ якщо знайдені в сегменті **менеджера** (`quoteMatch.findQuote({requireRole:'manager'})` → клієнтську репліку не можна видати за менеджерську). КОД привʼязує таймкоди. Кеш у `calls.behaviors` (`analysis_version=2`). **Раз на дзвінок** → звіти за період не переаналізовують дзвінки (закрило «брудну» генерацію).
- **REDUCE** (`bot/analyze.js: reduceFindings`, per-report, `OPENAI_REPORT_MODEL`=gpt-4o) — тягне кешовані `behaviors` **лише продажних** дзвінків періоду (`buildCandidates` пропускає `info`/`other`) + метрики, кластеризує в findings. Модель посилається на докази **лише за id** → вигадати цитату не може.
- **Код-верифікація** (`assembleFindings`, чиста, юніт-тестована): цитата re-верифікується проти сегментів **менеджера** свого дзвінка; один доказ підпирає лише ОДИН finding (дедуп); finding з <3 доказами викидається; «спершу помилки».
- **Перевірка релевантності** (`verifyFindingsRelevance`, окремий LLM-прохід `OPENAI_REPORT_MODEL`) — суворий рецензент вирішує, які цитати **справді доводять** claim; нерелевантні відкидаються, finding з < `MIN_EVIDENCE` підтвердженими валиться. Це закриває кейс «цитата існує, але не про те». Фейл API → graceful fallback на assembled (звіт не гине).
- **Аудіо** (`bot/audioClip.js`, системний ffmpeg) — лише під негативні findings, ≤3 кліпи/finding, ±`AUDIO_CLIP_PAD_SEC` навколо таймкоду; запис Binotel тягнеться на льоту й кешується на дзвінок у межах звіту. Нема ffmpeg → звіт іде текстом (preflight, не падає).
- **Звіт рендериться ЗАВЖДИ** (`deliverReport`): числовий header з розбивкою **всього / продажних / інформаційних** (конверсія й найслабший етап — по продажних) + findings; якщо findings нема — чіткий рядок «критичних патернів не зафіксовано» / «продажних дзвінків не було», а не «недостатньо матеріалу».
- **Доступ:** доказовий звіт бачать ЛИШЕ director/marketer.

Меню (inline-кнопки):

1. **Звіти** (`report.js` + `segments.js`) — планувальник (`setInterval` 30с звіряє київський час зі слотами). **Слоти — з `/settings` → «🕒 Час звітів» (`app_state.report_times`), не env** (дефолт `13:00,19:30`; порожній = нема). **Не окремий cron, а in-process інтервал** persistent-бота. **ПЕРСИСТЕНТНА АНАЛІТИКА ПО ВІДРІЗКАХ (Задача 3, Фаза 1):** дорогий REDUCE кешується в таблиці `report_segments` по **(менеджер × день-обмежений відрізок)**, тож звіти НЕ переаналізують уже пораховане. Відрізки — межі доби Київ, розбиті слотами (`time.js: kyivDaySegments` → `[00:00,слот1),[слот1,слот2),…,[остСлот,24:00)`, без дір). `assembleReport(name,start,end)` (`segments.js`) = **заморожені `scheduled`-відрізки (reuse або порахувати+зберегти) + живий "хвіст"** `[остання межа, now]`; числа завжди live по періоду. **Self-consistency:** заморожений відрізок аналізується `SEGMENT_CONSISTENCY_PASSES`(деф.3) разів, лишаються findings, підтверджені більшістю прогонів (`analyze.js: reduceFindingsConsistent`/`corroborate`) — він рахується РАЗ і замерзає. **Grace:** слот віддається лише через `SEGMENT_GRACE_MIN`(деф.10) хв після межі (щоб ретраї `pending_calls` встигли). **Self-heal:** якщо в НЕДАВНІЙ (≤24 год) заморожений відрізок доїхав спізнілий дзвінок (`call_ids` змінились) — його тихо перераховують. Планувальник (`maybeSendScheduledReport`) віддає кожен ще недоставлений слот сьогодні (дедуп `app_state.delivered_report_slots`), сегмент = `[попередня межа, слот]`. **«Звіт зараз»/`/report`** (`sendManualReport`, за сьогодні, стан розкладу не чіпає) → `assembleReport` reuse + **дедуп подвійного кліку** (ефемерний `manual_tail` з тим самим `call_ids` віддається без повторного аналізу).    - **Що embed'иться (`embedInput`):** не сирий чанк, а `<назва файлу> (стор. N)\n\n<текст>`. Ізольований уривок часто двозначний сам по собі («Він складається з двох частин…») — назва повертає тему. ⚠️ Зміна цього ЧИ чанкінгу вимагає `npm run kb:reindex`.
   - **Пошук — гібридний (`retrieve`), 4 шари:** (1) **multi-query** — `expandQueries` просить модель дати 3 переформулювання, embed'иться оригінал+варіанти, кожен шукається (`searchKbChunks`, по 8); (2) **лексичний прохід** (`searchKbChunksLexical` — Postgres FTS по `kb_chunks.tsv`) по сирому формулюванню: вектор розмазує точні технічні терміни (назва деталі, номер норми) в загальну тему, FTS їх ловить. Конфіг `simple` (українського стемера в Postgres немає), морфологія компенсується **префіксним tsquery** (`toPrefixTsQuery` → `двигун:* | клапан:*`, OR для recall, ранжує `ts_rank_cd`); (3) **RRF-фьюжн** (`RRF_K=60`) зливає всі списки ПО РАНГАХ — тож cosine-відстань і `ts_rank` не треба нормалізувати одне до одного; топ-24 кандидати; (4) **LLM-реранкінг** (`rerankChunks`, `gpt-4o-mini`, `RERANK_SCHEMA`) оцінює кожного кандидата 0-10 «чи СПРАВДІ тут відповідь» і викидає все під порогом `RERANK_MIN_SCORE=4`, лишає топ-8. **Порожній результат реранкінгу — легітимний**: у посібниках справді нічого дотичного, і відповідь це скаже, а не буде фантазувати навколо «сусіднього за темою» тексту. Реранкінг упав → graceful fallback на fused-порядок.
   - **Векторна й лексична половини падають НЕЗАЛЕЖНО (не міняти на «або-або»):** 2026-07-25 ендпоінт `/v1/embeddings` OpenAI віддавав 500 на ВСІХ моделях embeddings (перевірено з двох різних мереж; `/v1/chat/completions` тим часом відповідав 200), і за vector-only дизайну це кладе всю базу знань — бо запит користувача теж треба embed'ити. Лексичній половині не потрібно нічого, крім Postgres, тож тепер: немає векторів → `retrieve` повертає `{degraded:true}`, відповідь усе одно будується по FTS і **явно попереджає** «семантичний пошук тимчасово недоступний, шукав лише за словами з питання». Помилкою вважається лише втрата ОБОХ половин. Перевірено наживо саме під час того збою: лексичний шлях знайшов правильне місце в підручнику й відповів.
   - **Категорії/доступ (audience):** обидва пошуки фільтруються `audiencesForRole(role)`: `manager` → `manager`+`both`, `mechanic` → `mechanic`+`both`, `director`/`marketer` (admin) → усе (фільтр `null`). Механік не отримає посібник продажів і навпаки.
   - **Відповідь (структурована, `ANSWER_SCHEMA`):** модель повертає `{answer, usedSources[], usedGeneralKnowledge}`. **Дозволено ~10% загальних знань:** якщо фрагменти покривають лише частково — модель доповнює достовірними загальними знаннями (не галюцинуючи, не суперечачи посібникам) і ставить `usedGeneralKnowledge=true`. Відповідь — ВИСНОВОК своїми словами, стисло: переписувати фрагменти дослівно їй заборонено, бо самі фрагменти система показує окремо (див. наступний пункт).
   - **Формулювання в UI — БЕЗОСОБОВІ** (вимога власника, 2026-07-25): бот не пише про себе в першій особі. Не «Обробляю файл…», «я витягну текст», «шукав лише за словами», «Готую сторінки…», а «Файл обробляється…», «текст буде витягнуто», «пошук виконано лише за словами з питання», «Сторінки готуються…». Тримати цей стиль у всіх нових повідомленнях KB.
   - **ДОСТАВКА = відповідь + PDF-ВИРІЗКИ, автоматично (2026-07-25, за уточненням власника того ж дня):** раніше назва файлу у футері була діплінком, клік по якому надсилав **весь** 300-сторінковий підручник. Тепер користувач отримує **тільки текст відповіді й одразу за ним мініатюрні PDF з цитованими сторінками** — по одному на кожне використане джерело. **Ні текстових цитат, ні кнопок, ні «весь файл»** (перша ітерація мала блок `<blockquote>`-цитат і кнопки `kb:frag`/`kb:full` — власник сказав, що цитати не потрібні, потрібні саме вирізки, і кнопку на весь файл прибрати; відповідно `evidenceBlock`/`evidenceKeyboard`/`trimQuote`/`pagesLabel` і хендлери `kb:frag`/`kb:full` **видалені**, гейт у `featureOf` повернуто до простого «`kb:ask` = всім, решта `kb:*` = admin»). Механіка: `answerQuestion` → `{text, sources}`, де `answerSources(used)` = по документу (≤`MAX_EVIDENCE_DOCS`=3) змерджені діапазони сторінок (`mergeRanges`, ≤`MAX_RANGES_PER_DOC`=2, тож суміжні цитати дають ОДИН файл, а не кілька майже-однакових); `index.js` шле текст (`sendLong` тепер **повертає id надісланих повідомлень**), а потім `sendAnswerSources` під індикатором «надсилає документ» — кожна вирізка йде **Telegram-reply на перше повідомлення відповіді**, щоб файли візуально тредились під нею. `kbClip.js: sendDocExcerpt` ріже сторінки ±`KB_CLIP_PAD_PAGES` (деф. 1) через **pdf-lib**. Джерело **без сторінок** (DOCX/TXT або цитата без page-метаданих) вирізати нічим — тоді шлеться оригінал, бо це єдиний доступний доказ. Помилка нарізки логується й пропускається, але **не валить відповідь** (вона вже правильна). **Два кеші в `kbClip.js`:** оригінал — на ДИСК за `file_id` (`os.tmpdir()/obv-kb-cache`, переживає `pm2 reload`, інакше кожне питання перекачувало б десятки МБ), Telegram-`file_id` готової вирізки — у пам'яті за `docId:a:b`, тож той самий діапазон удруге віддається миттєво. Текст відповіді шлеться **простим текстом без `parse_mode`** — розмітки в ньому більше немає, тож і ламатися на іменах файлів із `_` нічому. Легасі-діплінк `/start kbdoc_<id>` лишився (у старих повідомленнях чату ті посилання ще живі).
   - Екран «📚 Файли»: у списку біля кожного файлу — категорія; деталі → 📄 Відкрити оригінал / **🔁 Змінити для кого** (`kb:audset`→`kb:audput`) / 🗑 Видалити (каскад) + «➕ Завантажити новий». `migrateKb()` guard'иться: нема pgvector → KB вимкнено, решта бота живе. **KB-екрани меню — простий текст без Markdown** (назви файлів з `_`); а от сама ВІДПОВІДЬ на питання — HTML (blockquote + екранування). Після відповіді бот **лишається в режимі питань** (`awaiting=kb_question`); вихід — `/menu`.
   - **Транзакційність інжесту:** `insertKbChunks` пише всі чанки одним `BEGIN`/`COMMIT` (батчі по 100 рядків одним multi-row INSERT) — раніше 333 окремі INSERT'и без транзакції означали, що падіння на середині лишало напів-проіндексований док із брехливим `chunk_count`. `replaceKbDocChunks` (для `kb:reindex`) так само атомарно: DELETE+INSERT в одній транзакції, тож док ніколи не шукається в напів-перебудованому стані.
5. **Промпти AI — ОДИН хаб** (`prompt.js`, команда `/prompt`, admin-only). **Було два окремі пункти меню й два майже дослівні модулі-клони** (`/prompt` для guidance-промпту звіту + `/rubric` для рубрики балу) — вони починали розходитись у формулюваннях, тож 2026-07-25 на прохання власника зведені в один: у нативному меню лишився **лише `/prompt`**, `/rubric` і `rubric.js` **видалені** (класи callback'ів `rubric:*` більше не існують, гейт у `featureOf` спрощено до `cq.startsWith('prompt')`).
   - **Структура:** `/prompt` → **хаб** із вибором, що редагувати (кнопки `🧠 Промпт аналізу ефективності` / `⭐️ Оцінка комунікації менеджера`, далі додасться `оцінка скрипту`) → **екран деталей** конкретної інструкції: 👁 переглянути поточний, ✏️ змінити, ↩️ скинути до стандартного, « Назад (у хаб), « Меню.
   - **Реєстр замість копій (`EDITABLE` у `prompt.js`):** екрани, callback'и й обробка вільного тексту — ОДНІ на всіх; кожен елемент реєстру дає лише `{key, button, title, about, effect, info, save, reset}`. **Додати третю інструкцію = один запис у `EDITABLE`**, стиль розійтись не може за побудовою. Callback'и: `prompt` (хаб), `prompt:o|v|e|r|rok:<key>`; вільний текст — `awaiting={type:'prompt', key}` → `savePromptText`.
   - **Формулювання екранів навмисно РОДОВО-НЕЙТРАЛЬНІ** («переглянути поточний», «скинути до стандартного», «використовується власний/стандартний **текст**») — саме українське узгодження за родом (`скинути промпт до стандартного` vs `скинути рубрику до стандартної`) і змушувало тримати два набори речень, через що вигляд і розійшовся. Свій `title`/`about` у кожної інструкції лишився, тож зрозуміло, що редагується.
   - **Що саме редагується:** (а) `analysis` → guidance-промпт reduce (тон/формулювання claim/why/action + готові фрази), `app_state.analyze_prompt`, `analyze.js: getAnalyzePrompt()` → він або `DEFAULT_REPORT_GUIDANCE`; (б) `score` → рубрика `communicationScore` (критерії балу 1-10, який AI ставить КОЖНОМУ дзвінку на інжесті, не в звіті), `app_state.score_rubric`, `core/classifyCall.js: getScoreRubric()` → вона або `DEFAULT_SCORE_RUBRIC` (анкерована шкала 9-10/7-8/5-6/3-4/1-2).
   - ⚠️ **Редагуються ЛИШЕ формулювання.** Структуру й гарантії забезпечує КОД, не промпт: JSON-схема findings, правило ≥`MIN_EVIDENCE` підтверджених цитат, дедуп і аудіо для негативу (`assembleFindings`), шкала 1-10, **таксономія 4 етапів (`core/stages.js`, НЕ редагована)**. Хоч би що написав власник, вигадані/недоведені твердження не проходять. Старий прозовий `DEFAULT_ANALYZE_PROMPT` прибрано; легасі-значення `app_state.analyze_prompt` одноразово скидається в `migrate()` (guard `analyze_prompt_v2`).

6. **Налаштування** (`settings.js`, команда `/settings` — **лише нативна, БЕЗ inline-кнопки**, admin-only) — керування двома списками отримувачів (обидва в `app_state` як JSON `{id,name}[]`, тому повідомлення розсилається кільком людям одразу): **«⚠️ Сповіщення про поломки»** (`alert_recipients`, куди `core/telegram.js: sendAlert` шле алерти інжесту) і **«📊 Щоденні звіти»** (`report_recipients`, куди йдуть авто-звіти). На екрані списку: кнопка `🗑 <ім'я>` на кожного (видалення одним тапом), «➕ Додати» → reply-клавіатура (`request_users` «Обрати з контактів» / «Поділитися контактом» / надіслати числовий ID чату — останнє для груп на кшталт `-5426146652`). Отримувач = Telegram chat_id (юзер, що натиснув Start, або група). Store-обгортки — `getRecipients/addRecipient/removeRecipient(kind)`. Крім двох списків отримувачів, тут же **«🕒 Час звітів»** (`app_state.report_times`, `getReportTimes/addReportTime/removeReportTime`): київські слоти щоденних звітів, кероване кнопковим пікером **година → хвилина (крок 10 хв)** — формат завжди канонічний `HH:MM`, ввести невалідне неможливо. Слотів може бути скільки завгодно; порожньо = звітів нема; дефолт (поки не задано) — `13:00,19:30`. Callback'и: `set:times` (список), `set:timeadd`→`set:timeh:<h>`→`set:timem:<h>:<m>` (додати), `set:timedel:<HHMM>` (прибрати). Gate — `featureOf` повертає `settings` для `set*` / `/settings` (admin-only). ⚠️ Замінило env-змінні `TELEGRAM_CHAT_ID`, `BOT_REPORT_CHAT_ID` і `BOT_REPORT_TIMES` (усі прибрані). Хендлери `message:contact`/`message:users_shared` у `roles.js` і `settings.js` пропускають чужий апдейт далі через `next()` — ланцюжок: roles → settings → save_phone (в `index.js`).

Бот НЕ пише в `calls`/`pending_calls` — лише читає; пише в `kb_docs`/`kb_chunks`, `bot_users` (ролі) і ключі `app_state` (звітні + `analyze_prompt` + `alert_recipients`/`report_recipients`).

### Ідентифікація оператора (`resolveManagerName` в `processCalls.js`)

**Джерело правди про ІСНУВАННЯ операторів — Binotel** (таблиці `managers` немає, клієнт керує операторами в Binotel). Але з 2026-07-24 **джерело правди про ТЕ, ЧИЙ це дзвінок на персональному номері — сам номер (`internalNumber`), а не ім'я, яке в цей момент повертає Binotel.**

- **Особистий номер** (903/904/905) → `manager_name` = **канонічне ім'я з фіксованої мапи `PERSONAL_OPERATORS`** (`processCalls.js`, дефолт `903=Роман,904=Андрій,905=Володимир`, override через однойменний env). Ім'я з Binotel (`employeeData.name`) для цих номерів **ігнорується повністю** — ні для збереження, ні для `identifyManager`.
- **Спільна слухавка** (номер у `SHARED_EXTENSIONS`, дефолт `901,902`) або будь-який ІНШИЙ номер без імені (не в `PERSONAL_OPERATORS`) → Binotel не знає, хто відповів, тому оператор визначається **з транскрипту**: `identifyManager.js` окремим OpenAI-запитом обирає, ХТО зі списку відомих операторів представився. Список кандидатів (**roster**) — динамічний, `getOperatorRoster()` = distinct не-числові `manager_name` з `calls`. AI обмежений `enum`'ом кандидатів, тож повертає точно одне з тих імен (сам зводить розмовні/RU-варіанти) або `null`. Збіг → це ім'я. Нема збігу/імені → лишається голий номер як мітка.
- **Виключені номери** (`EXCLUDED_EXTENSIONS`, дефолт `0674738200` — мобільний директора) → дзвінок **пропускається на самому вході** (`processOneCall`/`retryPendingCalls`), ще до транскрипції/аналізу: не зберігається в `calls`, не лишається в `pending_calls`. Директор — не продажник, і оцінка ефективності по ньому не потрібна.

⚠️ **Баг 2026-07 (виправлено):** для персональних номерів 903/904 Binotel періодично повертав `employeeData.name` ПУСТИМ (з невідомої причини — можливо, тимчасовий десинк після редагування імені співробітника в адмінці Binotel). Старий код тоді трактував це як спільну лінію і жену дзвінок через `identifyManager` — а той **іноді вгадував НЕПРАВИЛЬНОГО менеджера** за голосом/контентом (дзвінки з номера Романа/Андрія приліплювались до Володимира). Окремо, номер директора (0674738200) ніколи не мав `employeeData` і завжди йшов через `identifyManager`, регулярно забруднюючи статистику реальних менеджерів. Фікс: персональні номери відв'язані від `employeeName`/`identifyManager` повністю (мапа за номером), директорський номер виключений з інжесту. Історичні дані виправлено скриптом `normalize:operators` (див. «Команди»). **Урок:** для персональних номерів ідентифікація мусить бути за стабільним `internalNumber`, а не за іменем, яке може зникнути/змінитись на боці Binotel.

Тобто roster сам «наповнюється» з Binotel (для 901/902): як тільки менеджер зробив дзвінок з особистого номера, його канонічне ім'я стає кандидатом для матчингу спільних дзвінків. **Клієнт попросить операторів представлятись** на спільних — від цього залежить якість атрибуції 901/902.

`reattributeShared.js` (`npm run reattribute:shared`) — переганяє вже збережені спільні дзвінки (з голим номером) через ту саму AI-ідентифікацію по збережених транскриптах. `normalizeOperators.js` (`npm run normalize:operators`) — одноразовий фікс історії після бага вище (не плутати: це не про 901/902, а про персональні номери + видалення директора).

### Надійність (свідомі архітектурні рішення, не міняти без причини)

- **Чекпоінт замість вікна** — гарантує відсутність дір при збоях cron
- **`pending_calls`** — дзвінок, що впав на будь-якому кроці, ретраїться на кожному наступному `poll` (не втрачається), до `MAX_PENDING_ATTEMPTS` (20), потім `status='failed'` + Telegram-алерт, рядок лишається в таблиці для ручної перевірки (нічого не видаляється мовчки)
- **`withRetry`** (`retry.js`) — обгортає кожен зовнішній виклик (Binotel/OpenAI/Telegram), 2-3 спроби з наростаючою паузою
- **Binotel API-помилки з HTTP 200** (`core/binotel.js: callBinotel`) — Binotel віддає rate-limit та інші помилки (`{"status":"error","code":106,"message":"Requests are too frequent..."}`) з HTTP-статусом 200, тож перевірки лише `res.ok` НЕДОСТАТНЬО. **Виправлено 2026-07-24** (знайдено при діагностиці бага з номером клієнта): `callBinotel` тепер кидає помилку і при `data.status === 'error'`, не лише при HTTP-фейлі — інакше `listCallsForPeriod` мовчки повертав "0 дзвінків за період" замість ретраю, і чекпоінт міг просунутись повз період, який Binotel насправді не віддав (тихий data loss — прямо суперечить принципу надійності). Ретрай Binotel тепер `delayMs:2000` (було 1500) — 5-секундне вікно rate-limit'у Binotel краще покривається. `processCallsForRange` (спільна для лайв-полера й `backfill.js`) і `backfillClientNumbers.js` тепер додатково роблять коротку паузу (1.5с) між чанками, щоб не бомбардити список дзвінків без природного розриву (у звичайному інжесті пауза між чанками природна — транскрипція/аналіз кожного дзвінка займає час; у "легких" скриптах без такої роботи паузу додано вручну).
- **Telegram (інжест) — тільки алерти.** `core/telegram.js` лише `sendMessage`/`sendAlert` (вихідні), для сповіщень про збої й невідомих менеджерів. `sendMessage` ділить текст на шматки ≤4096 і має markdown→plain fallback. Шле через той самий єдиний бот `@OBVCarServiceWork_bot` (вихідні виклики не конфліктують з `getUpdates` бота звітності).

## Деплой

Детальна інструкція — `DEPLOY.md`. Коротко: VPS на **AlmaLinux 10**, обидва процеси тримає **pm2** (`ecosystem.config.cjs` у корені репо). **Два процеси з одного репо**: `obv-poller` (`node src/jobs/index.js`, pm2 `cron_restart: */15 * * * *`, `JOB_TYPE=poll`) і `obv-bot` (`node src/bot/index.js`, `autorestart`, постійно online). Обидва читають один `.env` з кореня. **Потрібен системний `ffmpeg`** (аудіо-кліпи доказового звіту; EPEL/RPM Fusion — див. DEPLOY.md). Після деплою — одноразово `npm run backfill:analysis` (таймкоди+behaviors для наявних дзвінків) і `npm run backfill:audio` (стягнути аудіо всіх наявних дзвінків у локальний архів `data/recordings`, ~50 хв на 800 дзвінків — запускати у `nohup`). **Папка `data/` не в git** — при `git pull` вона не чіпається, але й не переноситься на новий сервер сама. Автозапуск — `pm2 save && pm2 startup`. Оновлення — `git pull && npm install --omit=dev && pm2 reload ecosystem.config.cjs`.

## Механіка діалогу: перебивання і швидкість відповіді (`core/dialogueMetrics.js`, 2026-07-28)

Два сигнали «як менеджер ВЕДЕ розмову» (а не що каже), обидва рахуються **в КОДІ** з `calls.segments`:

- **Перебивання** — репліка КЛІЄНТА обривається на тире/трикрапці (`CUT_OFF_RE`), а далі говорить менеджер. ⚠️ **Ці тире ставить сама модель ElevenLabs, не наш код** (`core/elevenlabs.js: buildTurns` лише склеює текст реплік) — тобто ми цей сигнал ЧИТАЄМО, а не гарантуємо: відсутність тире не доводить, що перебивань не було. Заміряно на живій БД 2026-07-27: 44 обірваних репліки клієнта у продажних дзвінках, з них **42 (95%) продовжує саме менеджер**, присутні в 31% продажних дзвінків — рідкісний, але дуже точний сигнал. **Одинарна крапка НЕ рахується** (нею закінчуються 3499 із 5719 реплік клієнта — рахувати її означало б позначити майже кожен дзвінок).
- **Довгі паузи** — скільки клієнт чекав на відповідь: `наступна.start - поточна.end` для пари клієнт→менеджер, поріг `LONG_PAUSE_SEC` (деф. **4с**). Реальний розподіл у продажних: медіана 0.7с, p90 1.7с, >2с у 7.5% реплік, >4с у 1.9%.
- ⚠️ **Перекриття таймкодів свідомо НЕ використовується** як сигнал перебивання, хоча технічно доступне: 6% пар клієнт→менеджер мають від'ємну паузу, але перегляд показав, що це переважно артефакти діаризації — у звіт пішли б безпідставні звинувачення.

**Розподіл обов'язків: код рахує — LLM судить.** Код дає перевірювані ФАКТИ, модель вирішує, чи конкретний випадок є провтіком. Це не абстракція: перша ж знайдена наживо довга пауза (17.1с, дзвінок 6703840643) виявилась **законним переведенням дзвінка** — менеджер сказав «буквально дві хвилинки, побудь на линии» і передав клієнта колезі. Тому кандидат-пауза несе `prevManagerText` (попередня репліка менеджера) — саме там живе виправдання («секунду, зараз перевірю»), і без цього поля модель фізично не може відрізнити hold від мертвої тишини.

**Куди підключено:**
1. **Бал (`core/classifyCall.js`)** — `classifyCall(transcript, segments)` шле моделі **діалог із таймкодами** (`timecodedDialogue`) замість плоского транскрипту + блок замірів (`metricsPromptBlock`). Заміри інжектяться **поза рубрикою** навмисно: рубрика редагована власником, тож навіть якщо її перепишуть, числа до моделі однаково дійдуть — код дає факти, рубрика лише вагу. У `DEFAULT_SCORE_RUBRIC` доданий блок «КУЛЬТУРА ДІАЛОГУ» (одне перебивання — мінус; 3+ систематичних — не вище 6; пауза не карається, якщо менеджер попередив).
2. **Findings (`bot/analyze.js: dialogueCandidates`)** — перебивання й паузи стають кандидатами `type:'error'` поруч із поведінками з MAP-кешу. **Детекція в коді → працює ЗАДНІМ ЧИСЛОМ і безкоштовно**: `segments` уже збережені, тож історичні дзвінки дають ці кандидати без re-ingest і без жодного додаткового LLM-виклику. Цитата кандидата — репліка МЕНЕДЖЕРА (перебивна фраза / запізніла відповідь), тому вона проходить `verifyCandidate`(requireRole manager) і автоматично отримує аудіо-кліп. Промпт reduce окремо інструктує: пауза — помилка ЛИШЕ якщо не виправдана.
3. **Показ у звіті — лише findings**, окремого числового рядка в заголовку немає (рішення власника).
4. **Архів** — розмова рендериться з `segments` як `00:12 Менеджер: …` (`timecodedDialogue`) **на льоту**. `calls.transcript` навмисно НЕ змінюється: проти нього працює `core/quoteMatch.js` (пошук цитат для доказів), і префікси в кожному рядку його зламали б.

⚠️ **Замір ЇДЕ РАЗОМ із доказом (`evidence.note`) — не прибирати.** Прохід перевірки релевантності (`verifyFindingsRelevance`) отримує `{claim, quote}` і питає, чи цитата **сама по собі** доводить твердження. Перебивна фраза менеджера сама по собі перебивання не доводить (доказ — порядок реплік і таймкоди), тому рецензент **систематично вибивав** саме ці findings: перший наскрізний прогін на живому тижні з 6 замірами перебивань дав 0 findings про перебивання. Фікс: `verifyCandidate` кладе в доказ `note` (заміряний контекст), рецензент отримує його як поле `measured` з інструкцією «це ФАКТ, а не припущення; не вимагай, щоб перебивання було видне з цитати», а `report.js: findingText` друкує його під цитатою (`↳ клієнт не договорив: «…»`) — інакше директор бачить звичайну репліку менеджера й не розуміє, чому це доказ. Після фіксу той самий тиждень дає 2 findings: «перебиває клієнта на півслові» (6 доказів) і «надмірні паузи перед відповіддю» (3 з 4 замірів — один прохід релевантності відкинув як виправданий, тобто судження працює).

⚠️ **`assembleFindings` дедупить тепер і за ЦИТАТОЮ** (`callId|normalize(quote)`), не лише за id кандидата: з появою код-кандидатів той самий рядок менеджера може легітимно прийти двічі (як поведінка з MAP і як перебивання), і без цього одна цитата «доводила» б два різні findings — саме те, що правило «одна цитата = один finding» має не допускати.

## Звіт за період: аналіз по днях + зведення (2026-07-28)

«📊 Звіт за період» у «Статистиці менеджера» більше **не показує список днів** і більше не може відмовитись аналізувати період.

- **Було (режим `trend`):** числовий список по кожному дню + findings ЛИШЕ з уже заморожених `scheduled`-відрізків (reuse-only). Тому на періоді, за який ще ніхто не робив звіту, бот віддавав «ще немає заморожених відрізків аналізу» — і це, за словами власника, неприпустимо. Плюс сам список днів виглядав погано, а тижневу/місячну картину в числах і так дає екран «Динаміка».
- **Стало (режим `range`, `bot/segments.js: collectRangeFindings`):** період ріжеться на **КАЛЕНДАРНІ ДНІ Києва** (`enumerateDays`, `kyivDaySegments(cursor, [])`), кожен день аналізується **раз** і кешується в `report_segments` як `kind='day'`, далі перевикористовується назавжди. Потім `analyze.js: mergeFindings` зводить денні findings в **ОДИН цілісний список** за період — LLM лише ГРУПУЄ (повертає індекси), а КОД зливає докази (`applyMergeGroups`: дедуп за `callId|quote`, ≤`MAX_EVIDENCE_PER_FINDING`=6 доказів на finding, ≤`MAX_PERIOD_FINDINGS`=6 findings, помилки першими, тип не змішується). Тобто модель не може ні вигадати, ні продублювати цитату — та сама гарантія, що й у `assembleFindings`.
- **Чому день, а не слот:** `scheduled`-відрізки (3 на добу) існують як **незмінний часовий ряд РОСТУ**, привʼязаний до слотів звітів, і місяць — це ~90 таких. Доба — природна одиниця для звіту за період: ~20-30 одиниць на місяць замість 90, у кожній більше кандидатів (краща кластеризація), і кожна кешується.
- **Вартість/швидкість (заміряно наживо на місяці Романа):** 30 днів → 26 з дзвінками проаналізовано за **54с**, 17 денних findings зведено у **5** за 6с; **повторний виклик — 0с** (усе з кешу). День, у якому кандидатів < `MIN_EVIDENCE`, не коштує НІЧОГО (reduce замикається до LLM-виклику), і порожній результат теж кешується. Один прохід (`RANGE_PASSES=1`), а не `SEGMENT_CONSISTENCY_PASSES` — self-consistency потрібна замороженому ряду росту, який не перераховують; тут за неї платили б хвилинами. Дні аналізуються по `CONCURRENCY`=4 паралельно.
- **Квартал — свідомо `range_reuse` (reuse-only):** ~90 днів на натисканні кнопки — задорого, тож він збирає **все, що вже проаналізовано, будь-якої гранулярності** (`getStoredSegmentsInRange(..., ['day','scheduled'])` — і денні відрізки, і слотові від авто-звітів) і **честно пише в заголовку** «Аналіз є за N з M днів періоду — картина може бути неповною». Заміряно: 68 мс, 25 із 28 днів.
- **Порожній результат:** якщо продажних дзвінків не було — текст власника (`NO_SALES_TEXT`); якщо квартал ще нічого не має — пропозиція відкрити тиждень/місяць (вони проаналізують, і квартал далі спиратиметься на це); якщо продажні були, а патернів < порогу — точний рядок про це.
- ⚠️ **Режим у `expandKey` кодується ОДНИМ символом, а таймкоди — base36** (`d`/`r`/`q`/`l`, `MODE_CODE`): `callback_data` обмежена **64 БАЙТАМИ**, а `range_reuse:<10 цифр>:<10 цифр>:Володимир` — це вже 63 Б, і на довшому імені Telegram відкинув би всю клавіатуру (той самий клас баґу, що вже ловив `arch:call`). Стало 45 Б; base36 точний, період відтворюється до секунди. `expandKeyOf` ще й **логує** перевищення бюджету, щоб це не ламалось мовчки.
- `getDailyTrend` і `trendText` **видалені** (мертві), `getScheduledSegmentsInRange` → `getStoredSegmentsInRange(name, start, end, kinds)`.

## Термінологія в UI: «угода», а не «продажний» (2026-07-28)

Дзвінок, у якому є можливість записати клієнта чи продати, у **всіх** видимих користувачу текстах називається **«угода»** (`дзвінок-угода`, `угод: 5`, категорія `💰 Угоди`). Слово **«продажний» заборонене** — українською воно двозначне («корумпований»), і власник попросив прибрати його повністю. Що з цього випливає:

- Внутрішнє значення `calls.call_purpose = 'sales'` **не змінювалось** — це код, його ніхто не бачить. Перейменовано лише тексти.
- Іменник **«продаж/продажі» лишається дозволеним** («навички продажу», «етап продажу», «відділ продажів») — заборонений саме прикметник.
- LLM пише claim'и вільним текстом, тому заборона продублювана **в промптах**: `DEFAULT_REPORT_GUIDANCE` (reduce) і system-промпт `mergeFindings` містять блок «ТЕРМІНОЛОГІЯ: …називай «угода», НЕ вживай слово «продажний»». Без цього модель занесла б його у звіт сама. ⚠️ Guidance редагований власником — якщо він перепише текст, цей рядок треба зберегти.
- Перевірка: `grep -rn "продажн" src/` має давати ЛИШЕ ці два промпти (де слово згадане як заборонене) і англомовні комментарі-пояснення.
