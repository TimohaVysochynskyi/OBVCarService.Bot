# Звіт за весь період — як він влаштований

Документ для власника проєкту. Пояснює, що таке «Звіт за весь період», де він береться,
скільки коштує і що саме в ньому робить штучний інтелект, а що — звичайна арифметика.

---

## 1. Що це взагалі таке

Це **невеликий самодостатній сайт** — папка з файлами, яку можна відкрити подвійним кліком
і читати без інтернету. Усередині:

```
index.html        ← сама сторінка, усі тексти й числа
assets/app.css    ← оформлення
assets/app.js     ← поведінка (перемикачі місяців, вкладки менеджерів)
audio/*.mp3       ← вирізані фрагменти розмов під прикладами
```

Це **не** PDF і не картинка — це жива сторінка: можна перемикати місяці, відкривати приклади,
слухати аудіо прямо в браузері.

Та сама папка — це і те, що пакується в архів для Telegram, і те, що згодом
віддаватиме веб-сервер на субдомені. Двох різних версій не існує.

---

## 2. Два способи його зробити

### Спосіб А — команда в боті

У Telegram-боті: **`/globalreport`**

- працює (команда зареєстрована й доступна);
- лише **нативна команда** (та, що в списку біля поля вводу) — інлайн-кнопки для неї немає навмисно,
  щоб не перевантажувати меню;
- доступна **лише директору й маркетологу**; менеджер чи механік її не побачать;
- бот показує «⏳ Звіт за весь період готується» і надсилає **zip-архів** із підписом:
  скільки дзвінків, годин розмов, розподіл по категоріях, скільки відмов СТО, скільки аудіо-фрагментів.

⚠️ **У цього шляху є вбудований обмежувач витрат: 2 хвилини на аналіз.** Якщо за 2 хвилини
не встигло проаналізувати всі нові дні — звіт усе одно прийде, але з позначкою, що картина
неповна. Це свідомий запобіжник: команда з телефона не може випадково запустити багатогодинний
платний прогін.

### Спосіб Б — команда на сервері

```
npm run build:site                      # перезібрати звіт
npm run build:site -- --zip out.zip     # + запакувати архів
npm run build:site -- --no-analyze      # взяти лише вже готове, коштує рівно 0
```

Той самий код, тільки без доставки в Telegram, і **без обмежувача в 2 хвилини** — тому саме так
роблять повну збірку. Це і є спосіб оновлювати сайт на домені.

## 3. Скільки це коштує зараз

**Коротка відповідь: копійки, а часто взагалі нуль.**

Заміряно на реальних прогонах:

| Ситуація                                       | Час           | Ціна                          |
| ---------------------------------------------- | ------------- | ----------------------------- |
| Усе вже проаналізовано (нічого не змінилось)   | 0.6 с         | **$0**                        |
| З'явився один новий день                       | ~20 с         | **~$0.10-0.15**               |
| Перший прогін на порожньому кеші (вся історія) | кілька хвилин | дорого — робиться**один раз** |

### Чому раніше було $4 за прогін і $8 за два

Було **дві причини**, обидві виправлені:

1. **Зламаний ключ кешу.** Результат найдорожчого кроку зберігався з прив'язкою до «кінця періоду».
   Але кінець періоду зсувається щоразу, коли надходить новий дзвінок — тобто **кожен** звіт
   гарантовано «не впізнавав» свій же вчорашній результат і перераховував усе наново.
   Тепер результат упізнається за **вмістом**, а не за датою.
2. **Одноразовий прогрів історії.** Коли фіча тільки з'явилась, треба було проаналізувати всі
   ~200 днів. Це разова робота, вона більше не повториться.

### ⚠️ Єдине, що може знову зробити прогін дорогим

Команда `npm run backfill:blockers` **без** прапорця `--keep-cache` навмисно **стирає весь кеш
аналізу** (щоб перерахувати висновки з урахуванням відмов). Після неї наступний звіт прогріє
всю історію за повну ціну. Якщо кеш стирати не треба — запускайте з `--keep-cache`.

### Як дізнатись ціну ДО запуску, безкоштовно

Ціна = скільки пар «менеджер × день» мають дзвінки, але ще не мають збереженого аналізу.
Це рахується одним запитом до бази, без жодного звернення до OpenAI. Приклад реального заміру:

```
Роман      95 днів із дзвінками → аналізувати треба 1
Володимир  59 днів              → 0
Андрій     53 дні               → 0
```

Тобто 207 із 208 днів уже готові — прогін коштуватиме центи.

⚠️ **Чого робити НЕ можна:** колись використовувався трюк «запустити з навмисно неробочим ключем
і порахувати помилки». Так робити не можна — при збої система запам'ятовує **порожній** результат
як справжній і псує кеш. Саме через це одного разу у звіті лишились незлиті, майже однакові пункти.

## 4. Звідки беруться дані

Усе — з **однієї бази даних** на тому ж сервері. До Бінотелу під час збірки звіту практично
не звертаємось: записи розмов лежать у локальному архіві на сервері, і зараз він повний
(усі 1933 дзвінки). Бінотел смикається лише як запасний варіант, якщо якогось файлу на диску
раптом не виявиться.

Головні джерела:

- **`calls`** — по одному рядку на кожен оброблений дзвінок. Там лежить усе: розшифровка,
  репліки з таймкодами, хто менеджер, номер і ім'я клієнта, категорія дзвінка, оцінка,
  чи записався клієнт, чи представився менеджер, напрямок, шлях до аудіо.
- **`report_segments`** — «пам'ять» аналізу. Щоб не платити двічі за те саме.

У звіт потрапляють **тільки дзвінки з розшифровкою**. Кілька секундних дзвінків без мови
в числа не входять — про це сказано в самому звіті, у розділі «як це рахується».

## 5. Головне питання: що рахується просто так, а що через ШІ

Це найважливіше для розуміння ціни. У звіті **дві принципово різні половини**.

### Половина перша — ЧИСЛА. Безкоштовно, звичайні запити до бази

Сюди належить **майже все, що ви бачите**:

- скільки всього дзвінків, годин розмов, менеджерів;
- кільцева діаграма категорій (угоди / інформаційні / службові / особисті);
- розбивка вхідні-вихідні;
- усі 5 номерів із їхньою статистикою і розкладом «хто брав слухавку»;
- секція «Представлення» (хто називав ім'я та сервіс);
- таблиці угод, записів, конверсії, балів по місяцях;
- порівняння менеджерів, усі стовпчикові та лінійні графіки;
- таблиця відмов і причин;
- слабкі етапи воронки.

Усе це — **арифметика над уже збереженими даними**. Коштує нуль, рахується за частки секунди.
Тому перемикачі місяців у звіті працюють миттєво: числа всіх місяців уже лежать усередині файлу
в окремому блоці, а JavaScript просто підставляє потрібні.

### Половина друга — ВИСНОВКИ. Ось це і коштує гроші

Це блоки **«топ-3 сильних сторін»** і **«топ-3 слабких сторін»** у картці кожного менеджера,
з дослівними прикладами й аудіо. Вони не «збираються», а **аналізуються** окремо.

Тобто відповідь на ваше питання: **ні, це не просто збір даних із виведенням у графіки.**
Графіки — так, збір. А сильні й слабкі сторони — окреме дослідження в кілька проходів.

## 6. Ланцюжок аналізу: хто що робить

Робота свідомо розділена так, щоб **дорога частина виконувалась якнайрідше**.

### Крок 0 — під час збору дзвінків (не у звіті)

Щойно дзвінок надходить, по ньому одразу робиться розбір, і результат **зберігається назавжди**:

| Що визначається                                                   | Модель        |
| ----------------------------------------------------------------- | ------------- |
| Категорія дзвінка (угода / інформаційний / службовий / особистий) | `gpt-4o-mini` |
| Поведінки менеджера в розмові + дослівні цитати                   | `gpt-4o-mini` |
| Чи представився (ім'я + назва сервісу)                            | `gpt-4o-mini` |
| Успішність, найслабший етап, бал комунікації                      | `gpt-4o-mini` |
| Чи відмовило саме СТО (черга / немає деталі / не наш профіль)     | `gpt-4o`      |
| Чому пішов клієнт                                                 | `gpt-4o-mini` |

**Звіт цього вже не переробляє.** Він читає готове. Саме тому звіт за будь-який період
не коштує пропорційно кількості дзвінків.

### Крок 1 — висновки за день

Для кожного менеджера й кожного **дня** беруться збережені поведінки з усіх його дзвінків-угод
і зводяться в кілька пунктів на кшталт «перебиває клієнта на півслові».

Модель — **`gpt-4o`**. Результат зберігається в `report_segments` і більше **ніколи** не
перераховується. Саме тому другий звіт за той самий період безкоштовний.

⚠️ День, у якому було замало матеріалу, **не коштує нічого** — система навіть не звертається
до моделі. І порожній результат теж запам'ятовується, щоб не перевіряти щоразу.

### Крок 2 — перевірка на чесність

Окремий суворий прохід (теж `gpt-4o`) перевіряє кожну цитату: **чи вона справді доводить те,
що написано**. Цитати «не про те» викидаються. Якщо після перевірки в пункті лишилось
менше двох прикладів — пункт викидається цілком.

### Крок 3 — зведення за весь період

Денні висновки за всі місяці зводяться в **один цілісний список** на менеджера (`gpt-4o`).
Тут модель лише **групує** схожі пункти — зливає докази вже код, тому цитата не може ні
задублюватись, ні зникнути.

Результат зведення теж кешується. Якщо в менеджера нічого не змінилось — цей крок безкоштовний.

## 7. Чому звіт не може нічого вигадати

Це закладено в конструкцію, а не в прохання до моделі:

1. **Модель не бачить, куди писати цитату.** Вона посилається на докази **лише за номером** зі
   списку, який їй дали. Вигадати рядок розмови технічно нікуди.
2. **Код перевіряє кожну цитату заново** — шукає її серед реплік **саме менеджера** саме цього
   дзвінка. Не знайшлась — викидається. Репліку клієнта неможливо видати за слова менеджера.
3. **Один доказ підпирає лише один висновок** — та сама цитата не може «доводити» два різні пункти.
4. **Менш ніж два приклади — висновку немає.** Одиничний випадок не стає «патерном».
5. **Окремий рецензент за замовчуванням відкидає.** Якщо він не впевнений — пункт не проходить.

Це той самий принцип, що й у решті проєкту: **код дає перевірені факти, модель лише судить.**

## 8. Які саме промпти працюють

У звіті задіяні **три** тексти-інструкції, і ще кілька працюють раніше, на етапі збору дзвінків.

### Що можна редагувати самому, прямо з бота

Команда **`/prompt`** відкриває хаб із двома інструкціями:

| Пункт меню                         | Що змінює                                                                                      |
| ---------------------------------- | ---------------------------------------------------------------------------------------------- |
| 🧠**Промпт аналізу ефективності**  | тон і формулювання висновків у звіті — як саме описується проблема, чому це важливо, що робити |
| ⭐️**Оцінка комунікації менеджера** | критерії балу 1-10, який ставиться кожному дзвінку                                             |

⚠️ **Редагуються лише формулювання.** Правила «цитата має бути справжньою», «мінімум два приклади»,
шкала 1-10 і перелік етапів воронки забезпечуються **кодом**. Хоч би що там написати, недоведене
твердження у звіт не потрапить.

### Що редагується лише в коді

- **Зведення денних висновків** — інструкція «згрупуй схожі пункти», без свободи переписувати.
- **Перевірка релевантності** — інструкція суворого рецензента.
- Розбір кожного дзвінка на етапі збору: категорія, поведінки, представлення, відмови, причини незаписів.

---

## 9. Як влаштована «пам'ять» (кеш)

Уся економія тримається на таблиці `report_segments`. Там зберігаються результати аналізу:

| Вид запису  | Що це                                               |
| ----------- | --------------------------------------------------- |
| `day`       | висновки за один день одного менеджера              |
| `global`    | зведений список за весь період для одного менеджера |
| `scheduled` | відрізки для щоденних звітів у боті                 |

Правила прості:

- **день аналізується один раз і назавжди** — дані за минулий тиждень не змінюються;
- **зведення впізнається за вмістом** — якщо набір висновків не змінився, воно береться готовим;
- нові дні додаються **по одному**, тому щоденна перезбірка звіту коштує центи.

---

## 10. Аудіо під прикладами

Під кожним прикладом — і під сильними сторонами, і під слабкими — стоїть маленький плеєр
із фрагментом справжньої розмови.

- фрагмент вирізається **один раз** і далі перевикористовується всіма наступними збірками
  (реальний замір: «вирізано 0, узято готовими 38»);
- ріжеться з **локального архіву записів на сервері** — до Бінотелу при цьому не звертаємось взагалі;
- плеєр з'являється, **лише якщо** в цитати є таймкод і нарізка вдалася. Немає плеєра — цитата
  все одно лишається доказом; аудіо це зручність, а не умова.

⚠️ У ~140 дзвінків, які колись дозбирувались дешевим шляхом, немає таймкодів — у них
плеєрів не буде, поки їх не переобробити.

## 11. Що всередині сторінки, згори вниз

1. **Шапка** — період, кількість менеджерів, скільки годин прослуховування це замінило.
2. **Категорії дзвінків** — кільцева діаграма + таблиця з розбивкою вхідні/вихідні.
3. **Номери** — картка на кожен із 5 внутрішніх номерів. Стаціонарні (рекламні) стоять першими,
   у них ще й таблиця «хто брав слухавку» з колонкою `None` — це дзвінки, де менеджер не назвався.
4. **Представлення** — чи називає менеджер ім'я та сервіс (лише персональні номери).
5. **Менеджери** — вкладка на кожного: категорії, таблиця показників, графіки,
   топ-3 сильних і топ-3 слабких сторін із прикладами й аудіо.
6. **Порівняння менеджерів** — смужки й лінійні графіки по місяцях.
7. **Чому клієнт не записався** — відмови СТО та причини з боку клієнта, з іменами й телефонами.
8. **Слабкі етапи воронки.**
9. **«Як це рахується»** — методика простими словами, прямо в документі.

---

## 12. Куди воно потрапляє і хто це бачить

- Постійне місце на сервері: папка `data/report-site` (налаштовується змінною `REPORT_SITE_DIR`).
- У Telegram іде **zip з усією папкою** — розпакував, відкрив `index.html`, усе працює офлайн.
- Ця ж папка призначена для субдомену, коли клієнт його підніме.

⚠️ **Два важливі застереження про приватність:**

1. У звіті є **імена й телефони клієнтів, а також записи їхніх розмов**. Тому згенерована папка
   ніколи не потрапляє в Git — репозиторій публічний.
2. **З нашого боку захисту доступу немає.** Хто має посилання на субдомен — має і записи розмов.
   Пароль на субдомен ставить клієнт самостійно.

## 13. На що дивитись, якщо щось не так

| Симптом                                      | Найімовірніша причина                                                                             |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| У звіті немає сильних/слабких сторін         | не вистачило матеріалу (потрібно ≥2 приклади однієї поведінки) або кеш аналізу був щойно очищений |
| Позначка «покриття неповне»                  | частина днів ще не проаналізована — повторіть збірку, вона продовжить з того місця                |
| Немає плеєрів під цитатами                   | у тих дзвінках немає таймкодів (стара дешева розшифровка)                                         |
| Звіт раптом став дорогим                     | найімовірніше перед цим запускали`backfill:blockers` без `--keep-cache`                           |
| Три майже однакові пункти в одного менеджера | зведення не відпрацювало — перезберіть звіт звичайною командою                                    |

## 14. Мінісловник

- **Findings / висновки** — пункти «топ-3 сильних / слабких сторін».
- **Кеш аналізу** — збережені результати, щоб не платити двічі.
- **Стаціонарні номери** — 901 і 902, ті, що йдуть у рекламу.
- **Персональні номери** — 903 / 904 / 905, у кожного свій власник.
- **`None` у таблиці номерів** — дзвінки, де менеджер не представився, тож система не знає, хто говорив.
- **Угода** — дзвінок, у якому була можливість записати клієнта чи продати.
